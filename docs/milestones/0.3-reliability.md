## Investigation and closure requirements

Page-budget exhaustion is observed; precise delay attribution, causation and
mitigation remain unresolved. Distinguish this issue from sandbox Unix EPERM,
subprocess stdout loss and the native async-ID assertion. Do not classify it as
environmental solely because focused or ordinary-user reruns pass.

Use focused, instrumented reproductions before expensive full reruns. Preserve
exact runtime/execution context, concurrency, sanitized phase/error diagnostics,
commit/cancellation boundaries and failing logs. Any proposed correction must retain
bounded execution, storage consistency, cancellation and sibling isolation; raising
budgets, reducing concurrency or weakening assertions merely to obtain a pass is
not closure evidence. Require a demonstrated cause or bounded attribution, reviewed
mitigation and applicable focused/full regression evidence before resolving this
issue. No fix, acceptance waiver or deployment authorization is recorded here.


## Package lifecycle investigation follow-up (2026-10-18)

The shared kernel ledger now exposes a trusted `wydgit.execution-meter/1` snapshot:
elapsed time, unchanged effective time limit, charged counters and the first
terminal resource (`timeMs`, counter name, `guard` or `closed`). Trusted host
`execution.observeBudget` can collect these without putting identities, contexts,
capabilities, provider handles or exception data into HTTP responses/logs. The
existing Contact/drain assertions retain the last eight snapshots on failure.
No execution limit, concurrency or existing assertion was relaxed.

This distinguishes cancellation/closed-ledger follow-on LIMIT from actual wall-time
or counter exhaustion; it does not attribute the historical full-suite failures to
a particular I/O wait or scheduler delay. The issue remains **open**, pending a
metered failing trace and bounded phase/delay attribution followed by an evidenced
mitigation. Focused HTTP/security and the six existing controlled deadline probes
pass in the ordinary-user environment; see the lifecycle verification record for
commands and final full-suite results. Sandbox local-listener denials are tracked
separately and are not evidence of a runtime deadline defect.

## Checkpointed lifecycle continuation (2026-10-18)

Trusted server Page meters now include `wydgit.page-diagnostics/1`: first failing
phase, bounded phase durations and authorization/service/dispatch spans. The
observer runs after admitted storage work settles, preserving actual awaited
service duration even when Page execution already timed out. The shared ledger,
1,000 ms ceiling, parent/child accounting, concurrency and HTTP assertions are
unchanged. Diagnostics do not include App/session/package IDs, request values,
paths, contexts or provider handles; observer failures cannot affect responses.

The six controlled HTTP probes now assert the first resource and context:
JSON/SQLite precommit and JSON submitted-commit waits exhaust `timeMs` during the
Page action, with over 1,000 ms in the awaited service span. Connection-loss probes
record first resource `guard` during the action, without treating generic LIMIT as
timeout proof. A held native Page.Load records load/dispatch wall time and the same
shared Page time ceiling while sibling requests survive. Commit uncertainty,
precommit cancellation and admitted-I/O drain assertions remain unchanged.

The first continuation full suite had one package-boundary regression and no
Contact/drain failure. The boundary regression was corrected through an optional
trusted WydStore host export. **Historical attribution remains unresolved**:
controlled awaits establish diagnostic coverage, not the cause of an old
unmetered failure. See the [continuation evidence](0.3-package-lifecycle/qualification-2026-10-18.md).
